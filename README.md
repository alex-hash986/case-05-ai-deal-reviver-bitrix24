# AI Deal Reviver для Bitrix24

Зависшие B2B-сделки остаются в активной воронке и затрудняют прогноз выручки. Менеджеру приходится вручную читать историю, отличать реальную паузу от запланированного контакта и заново готовить касание. Reviver выделяет сделки с нарушенным SLA, оценивает риск по каждой карточке и готовит черновик для решения менеджера.

## Как работает решение

1. **Сканирование.** По каждой выборке стадий SQLite WAL хранит инкрементальный курсор `DATE_MODIFY + ID`. Повтор запроса с тем же ключом идемпотентности возвращает сохранённый результат.
2. **Отбор и прогноз.** Детерминированный `Decimal`-скоринг связывает сумму сделки с индексом стагнации и базовой вероятностью её стадии. Правило cooldown (`CooldownGuard`) ограничивает повторные касания. Отбор также учитывает SLA, запланированные дела, отказ клиента и очередь одобрения.
3. **Черновик.** `CommercialPolicyGuard` проверяет сообщение и следующее действие на неподтверждённые коммерческие условия. При недостатке контекста или сбое модели сделка направляется на ручную проверку.
4. **Human-in-the-Loop.** В live-профиле сводка появляется в таймлайне CRM. API проверяет токен и текущего ответственного за сделку либо полномочия РОП. Одобренное касание становится задачей менеджеру, привязанной к сделке. `bitrix_steps` хранит квитанции, а reconcile ищет уже созданную запись после неоднозначного ответа.

## Запуск на Windows

```powershell
py -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt
if (!(Test-Path .env)) { Copy-Item .env.example .env }
.venv/Scripts/python -m scripts.start_api
```

Во втором терминале из корня проекта:

```powershell
.venv/Scripts/python -m scripts.start_ui
```

- [Live Demo, очередь и Executive ROI-дашборд](http://127.0.0.1:8505)
- [Swagger](http://127.0.0.1:8015/docs)
- [Проверка API и SQLite WAL](http://127.0.0.1:8015/health)

**Mock.** Оставьте `BITRIX_MODE=mock` и `LLM_MODE=mock`. В Live Demo нажмите «Сканировать воронку», затем одобрите или отклоните карточку в очереди. Для повторного демо используйте новый файл `DATABASE_PATH`, чтобы начать с пустого курсора.

**Live.** Настройте `BASE_URL`, `API_KEY`, `FAST_LLM_MODEL`, `SMART_LLM_MODEL`, фактические тарифы в рублях и лимиты в `.env`. Для проверки модели на синтетическом корпусе оставьте `BITRIX_MODE=mock`. Для пилота CRM задайте `BITRIX_MODE=live`, отдельный файл БД, HTTPS-вебхук и токены одобрения. Для работы API с моделью включите `LLM_MODE=live` после preflight. [Регламент и параметры портала](docs/operations.md)

**On-premise Ollama.** Загрузите локальные модели под именами из `FAST_LLM_MODEL` и `SMART_LLM_MODEL`. Задайте `BASE_URL=http://127.0.0.1:11434/v1`, `API_KEY=ollama`, `LLM_MODE=live` и явные нулевые токенные тарифы для собственной машины. Сервер и эксплуатация учитываются отдельно в TCO. [OpenAI-совместимый API Ollama](https://docs.ollama.com/api/openai-compatibility)
