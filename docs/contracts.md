# Контракты Фазы 1 · ADR-001

Фаза 1 использует структуру src/core, src/domain, src/integrations, src/api и src/ui.
Внешняя CRM изолирована типизированным портом. Live REST и транспорт MCP предусмотрены для Фазы 2.
Управление выполняется локально с доверенным доступом к 127.0.0.1. Идентификация
менеджера и разграничение доступа требуются до подключения боевой CRM.

## HTTP

- GET /health проверяет доступность SQLite WAL.
- POST /api/v1/reviver/scan требует Idempotency-Key. Принимает stages, limit, session_id.
  Список стадий нормализуется. Для каждой комбинации стадий хранится отдельный курсор.
  Повтор с тем же ключом возвращает исходный снимок. Другой payload получает 409.
- POST /api/v1/reviver/approve/{revival_id} принимает {approve: bool}.
  Повтор того же решения возвращает текущее состояние. Изменение решения получает 409.
- POST /api/v1/reviver/reconcile повторяет незавершённые записи CRM.
- GET /api/v1/reviver/queue возвращает текущее состояние карточек и синхронизации.
- GET /api/v1/metrics рассчитывает показатели из сохранённых решений и прогонов.

## Хранилище и система скоринга

- scan_runs хранит хэш нормализованного запроса, ответ и телеметрию, включая точные расходы.
- scan_cursors хранит непрозрачный курсор Bitrix по фильтру стадий.
- revival_items хранит текущее решение, касания хранятся отдельно в touch_history.
- bitrix_steps хранит запланированные операции, попытки, состояние и квитанции.
- mock_receipts фиксирует результат операции по стабильному идентификатору.
- Единственный API-процесс владеет файлом SQLite. Запись, сканирование и replay сериализуются.
- Сохранение пачки, курсора и исходящих шагов атомарно. Переотправка сверяет квитанции.
- Сделка просрочена при days_in_stage > SLA. Давность без контакта уточняет индекс.
- Риск = сумма сделки × индекс / 100. Ожидаемое восстановление = риск × вероятность.
- Вероятность — эвристика, выраженная долей от 0 до 1. Денежные поля округляются до копеек.
- Cooldown начинается при постановке карточки реанимации в очередь.
- Клиентский текст в mock превращается в задачу менеджеру после явного одобрения.
- Коммерческие условия разрешены при точном совпадении подтверждённой фразы в политике и карточке.

## Дополнение Фазы 2

- `ApprovalIn.approver_user_id` — положительный целочисленный ID пользователя Bitrix24.
  В live обязательны ID и `X-Approval-Token`. Несовпадение токена или прав даёт HTTP 403.
- Право определяет текущий ответственный открытой сделки из `crm.deal.get` или список РОП.
  Итоговое решение сохраняет ID пользователя, а одобрение обновляет время в touch_history.
- Live публикует комментарий при постановке в очередь и задачу с текстом касания при одобрении.
- Квитанции записываются как JSON с `comment_id` или `task_id` в bitrix_steps.receipt.
  Таблица live_writes фиксирует начало отправки. При потере ответа reconcile ищет маркер
  операции в CRM и Tasks. При отсутствии подтверждения операция остаётся pending.
- Курсор live включает DATE_MODIFY и ID. При продолжении сначала читаются записи с той же
  датой и большим ID, затем записи с более новой датой.
- Код варианта записывается в scan_runs.ab_variant. Незавершённый скан привязан к исходному варианту.
