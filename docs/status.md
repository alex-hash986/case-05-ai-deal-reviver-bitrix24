# Состояние проекта Case 05 · AI Deal Reviver Bitrix24

Срез на 20 ноября 2026 года.
Контуры `@ops` и `@biz`. Завершены замеры и упаковка Фазы 3.
Сценарий — от сканирования воронки до задачи менеджеру по одобренному касанию.

## Архитектура

- Инженерный стандарт v2.2 размещён в docs.
- ADR-001 и HTTP-контракты изложены в docs/contracts.md.
- За основу ядра взят код Case 04 с контрактными подходами Case 03.
- Домен определяет скоринг, правила отбора, очередь и процесс одобрения.
- Bitrix24 подключается через типизированный порт.
- FastAPI связывает зависимости. Streamlit работает через HTTP API.
- Используется один локальный API-процесс на файл SQLite.

## Core и хранение

- SQLite WAL сохраняет прогоны, очередь, курсоры, операции и касания.
- Повтор Idempotency-Key воспроизводит исходный снимок сканирования.
- Повтор ключа с изменённым payload получает HTTP 409.
- Курсор учитывает DATE_MODIFY и ID сделки, хранится по набору стадий.
- Обновление курсора и публикация журнала запланированных операций атомарны.
- Запуск live требует отдельного файла БД, привязанного к порталу.
- Сохраняются токены, точные расходы, режим LLM и A/B-вариант.
- Бюджет контролируется до вызова по циклу и сессии.
- Публичная стоимость округляется до копеек по ROUND_HALF_UP.
- FAST, SMART и EMBEDDING используют один OpenAI-совместимый клиент.
- Черновик использует SMART. Ollama настраивается через локальный endpoint.

## Скоринг и правила

- Порог SLA и базовая вероятность задаются для каждой стадии.
- Индекс стагнации учитывает превышение SLA и давность касания.
- Риск и финансовый прогноз рассчитываются детерминированно в Decimal.
- SLA, будущие дела CRM, cooldown и уже ожидающие карточки блокируют повторный отбор.
- Отказ клиента, покупка у конкурента и конфликтная эскалация блокируют касание.
- При недостатке истории фиксируется сигнал для ручной проверки.
- Guard проверяет клиентский черновик и следующее действие до записи в очередь.
- Проверяются скрытые обещания бонуса, дисконта, фиксации цены и бесплатных услуг.
- Разрешённая формулировка совпадает с условием в политике и карточке.
- `variant_a` v1.0 — сервисный чек-ин и открытый вопрос.
- `variant_b` v1.1 — фоллоу-ап по артефакту или задаче клиента.

## Bitrix24 и интерфейс

- Режимы mock и live выбираются через BITRIX_MODE.
- Live читает открытые RUB-сделки, комментарии в таймлайне и CRM-дела.
- Сводка публикуется в таймлайн. Одобренное касание становится задачей с UF_CRM_TASK.
- Решение требует ID и индивидуальный токен в live. Чужому менеджеру возвращается HTTP 403.
- Проверяется текущий ответственный в Bitrix24 или полномочия руководителя из конфигурации.
- Одобрение сохраняет ID менеджера и обновляет запись в touch_history.
- Между REST-вызовами выдерживается интервал не менее 0,5 с.
- При 429 и 503 чтение повторяется с экспоненциальной паузой. После неоднозначной записи сверяется маркер.
- В bitrix_steps сохраняются удалённые comment_id и task_id.
- В очереди Streamlit доступны ID и токен менеджера, в ROI-вкладке показан последний A/B-отчёт.
- На 127.0.0.1:8015 повторно проверен health с SQLite WAL.
- На 127.0.0.1:8505 health Streamlit вернул HTTP 200.

## Live preflight и A/B

- `python -m ops.runners.preflight_live` проверил явные параметры шлюза и тарифы.
- Первый запрос получил HTTP 400, связанный с `response_format`. После указания JSON в сообщении шлюз вернул ожидаемый объект и учёт токенов.
- Успешный отдельный preflight занял 3 199,594 мс, 20 токенов входа и 1 токен выхода.
- Тарифная стоимость preflight — 0,00036 ₽, до копеек — 0,00 ₽ по ROUND_HALF_UP.
- `BITRIX_LIVE_SKIPPED: webhook not configured`. Проверки боевого Bitrix24 ожидают тестового портала.
- `python -m ops.runners.benchmark_ab --live-llm` прошёл на 60 синтетических сделках для каждого варианта через mock CRM.
- Общая стоимость live A/B со встроенным preflight — 0,75117 ₽ по токенам и тарифам при лимите 5 ₽. Бюджетных пропусков нет.
- A: p50/p95 — 1 765,914 / 2 580,172 мс, стоимость 60 циклов — 0,351735 ₽.
- B: p50/p95 — 1 708,452 / 3 531,419 мс, стоимость 60 циклов — 0,399075 ₽.
- Точность отбора A/B — 30/60 и 43/60. Точность причин — 16/46 и 19/46.
- Контрольные исключения сохранены во всех 24 случаях в каждом варианте.
- Подтверждённых нарушений среди выпущенных черновиков — 0/6 и 0/19. Guard заблокировал три генерации B.
- Live-метрики сохранены в docs/benchmark_ab_report.json и docs/benchmark_ab_report.md.

## Найденные проблемы

- При неопределённом результате записи без доступной квитанции операция ждёт сверки.
- Live зафиксировал `llm_unavailable` в 30 случаях A и 14 случаях B. Контур `@dev` должен раздельно диагностировать ответы шлюза и валидацию черновика перед пилотом.
- Для оценки точности прогноза и прироста выручки нужны фактические исходы сделок и контрольная группа.
