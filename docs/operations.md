# Эксплуатация Case 05

Запустите API и UI командами из README. Проверьте `GET /health` и
`http://127.0.0.1:8505/_stcore/health`. API работает одним процессом
на файл SQLite. Профиль по умолчанию использует локальный mock Bitrix и LLM.

`python -m ops.runners.smoke` создаёт временную БД, сканирует 12 сделок,
подтверждает один черновик и печатает метрики из сохранённых решений.
Для повторного демо используйте отдельный `DATABASE_PATH`; курсор в
существующей базе уже указывает на обработанные сделки.

Если вызов сканирования прервался, повторите исходный payload с тем же
`Idempotency-Key`. Для незавершённых записей CRM вызовите reconcile. Результат
чтения и квитанции мок-записей сохраняются в SQLite.

Для Ollama установите `LLM_MODE=live`, `BASE_URL=http://127.0.0.1:11434/v1`,
`API_KEY=ollama`, имена ролей и явные нулевые тарифы. Для облачного шлюза
укажите фактические действующие тарифы в рублях за миллион токенов входа
и выхода. Фаза 1 использует SMART для черновиков. FAST и EMBEDDING доступны
через общий шлюз. Один session_id объединяет расходы серии сканирований.
Неизвестный расход после неоднозначного вызова блокирует новые вызовы сессии.

## Фаза 2

- `python -m ops.runners.build_deals_60` воспроизводит синтетический корпус.
- `python -m ops.runners.benchmark_ab --mock-llm` сохраняет JSON и Markdown в docs.
  `--live-llm` использует настроенный LLM Gateway и сохраняет режим, токены, точную Decimal-стоимость
  и причины пропусков. Общий лимит включает preflight и два равных лимита вариантов.
  Синтетические выигрыши проверяют расчёт калибровки. Для оценки прогноза нужны закрытые сделки.
- Для live используйте отдельный `DATABASE_PATH`, `BITRIX_MODE=live` и HTTPS
  `BITRIX_WEBHOOK_URL` с правами чтения CRM, записи комментариев и чтения/создания задач.
  Укажите идентификаторы стадий портала в config/stage_sla.yaml. Текущий профиль рассчитан на RUB.
  `BITRIX_INITIAL_MODIFIED_SINCE` ограничивает первый импорт, если указан.
- `BITRIX_APPROVER_TOKENS` — JSON-объект с индивидуальными токенами по ID пользователей.
  `BITRIX_SUPERVISOR_IDS` — JSON-массив ID руководителей с правом принять решение по чужой сделке.
  В UI менеджер вводит свой ID и токен. API принимает токен в заголовке X-Approval-Token.
- `BITRIX_VERIFIED_TERMS_FIELD` может указывать на поле CRM с подтверждённой формулировкой.
  Ограничьте редактирование поля и задайте разрешённые фразы в config/commercial_policy.yaml.
- После неоднозначного сбоя повторите reconcile. При отсутствии удалённой квитанции
  операция остаётся ожидающей сверки. Для ручного разрешения проверьте исход операции в CRM.

## Фаза 3 · Live preflight и A/B

Из корня проекта:

```powershell
python -m ops.runners.preflight_live
python -m ops.runners.benchmark_ab --live-llm
```

Live A/B сам выполняет preflight. Для минимизации расходов автоматизированного
прогона достаточно второй команды. Отдельно запущенный preflight имеет свой
лимит и учитывается провайдером отдельно.

Требуются явные `BASE_URL`, `API_KEY`, `FAST_LLM_MODEL`, `SMART_LLM_MODEL`,
`LLM_RUB_PER_MILLION_INPUT_TOKENS`, `LLM_RUB_PER_MILLION_OUTPUT_TOKENS`,
`MAX_CYCLE_COST_RUB` и `MAX_SESSION_COST_RUB`. Раннеры также принимают
`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL_FAST` и `LLM_MODEL_SMART`.
Для запуска API используйте канонические имена из `.env.example`.
Preflight проверяет конфигурацию обеих ролей и вызывает SMART, которую использует Reviver.
Для запроса проверяются JSON-режим, токены и тарифная стоимость с округлением до копеек.

При настроенном вебхуке выполняется read-only `method.get` по четырём методам.
Статус `BITRIX_SCOPE_OK` подтверждает доступность по scope. Права пользователя
на конкретные сделки и постановку задач проверяются на тестовом портале.
[Спецификация Bitrix24 method.get](https://apidocs.bitrix24.com/api-reference/common/system/method-get.html)

A/B читает синтетический корпус через mock Bitrix24 и отдельные временные БД.
Остаток бюджета после preflight делится между вариантами поровну. Если консервативная
оценка не помещается в лимит цикла или варианта, решение учитывается как бюджетный пропуск.
При неизвестном расходе дальнейшие платные вызовы останавливаются и сохраняется предыдущий отчёт.
Для нового размещения отчётов задайте `--output-dir`.
